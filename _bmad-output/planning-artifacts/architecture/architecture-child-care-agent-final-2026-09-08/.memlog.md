- (decision) [ADOPTED] Use a layered, capability-oriented architecture: agent interpretation, minimal skills, MCP boundary/orchestration, Apex source retrieval, TypeScript normalization, and Python deterministic evaluation. This prevents business logic from drifting into prompts or transport code.
- (decision) [ADOPTED] The authenticated provider scope is established inside MCP and Apex; model input may select capability and bounded filters but never provider identity, authorization scope, or unrestricted records. This prevents cross-provider access and identity drift.
- (decision) [ADOPTED] Each provider-facing action has one composite MCP capability owner. The general server registers and dispatches tools, but attendance, confirmation, absence-limit, and payment orchestration live in domain modules. This prevents duplicated fan-out and competing formatters.
- (decision) [ADOPTED] TypeScript owns transport, validation, scope injection, source mapping, normalization, orchestration, and provider-safe result shaping; Python owns deterministic rules, date logic, counts, classifications, and money calculations. This prevents arithmetic and source joins from being reimplemented in multiple layers.
- (decision) [ADOPTED] Apex is an authoritative read-only source and secondary authorization guard. It retrieves Salesforce records and preserves source relationships; it does not interpret conversational intent or calculate provider-facing risk.
- (decision) [ADOPTED] Canonical contracts are explicit at the MCP-to-evaluator boundary; identifiers, dates, money, freshness, provenance, capability, and error status are structured. Unknown or ambiguous source fields fail closed rather than being inferred.
- (decision) [ADOPTED] Generated output is never hand-edited and is not a source of truth: mcp/cccap-provider-api/dist is rebuilt from src, and skills/reports/eval-runs is historical evaluation output. Runtime source remains .github/agents, skills, mcp/src, Python scripts, and CHATS_SIT Apex.
- (assumption) [ASSUMPTION] The first maintainability pass should reorganize documentation and ownership before physically moving runtime modules; current green tests and MCP registration make a map-first refactor lower risk.
- (decision) [ADOPTED] Current identity scope is initialized once per MCP process from the Salesforce CLI authenticated user; production Apex-side identity derivation is explicitly deferred. This prevents local process behavior from being mistaken for the production authorization design.
- (decision) [ADOPTED] Every capability must expose one request entrypoint, one canonical input adapter, one evaluator invocation, and one provider-safe result contract. MCP schemas, TypeScript normalizers, and Python evaluators own validation at their respective boundaries.
